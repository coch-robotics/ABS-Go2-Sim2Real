Reproduction Overview

Original work. Agile But Safe (ABS, RSS 2024) enables quadrupeds to move through cluttered environments at high speed while avoiding collisions. An Agile Policy pursues speed, while a Recovery Policy takes over when risk rises. A safety threshold based on a Reach-Avoid (RA) value function coordinates the switch between them. A separate Ray Prediction Network estimates obstacle-distance rays from camera observations.

Scope of this reproduction. Rather than merely running the official code, this project adapts ABS to a different hardware platform: Unitree Go2 + RealSense D435i (forward depth to 2D rays) + Livox MID360 (side/rear 2D LiDAR observations and LIO localization). The displayed hardware validation focuses on the Agile Policy deployment path. The emphasis is on quantifying and narrowing the Sim-to-Real gap: measuring latency, payload, and motor characteristics on the robot, then feeding those measurements back into simulation (Real-to-Sim) for domain randomization. Training is performed in Isaac Gym, with deployment through a set of ROS nodes.

System Overview

Simulation

The simulation work builds on the official ABS code (training/legged_gym + training/rsl_rl) and Isaac Gym Preview 4. The original method trains four components: (1) an Agile Policy (PPO), (2) a Recovery Policy, (3) a Reach-Avoid (RA) value network, and (4) a Ray Prediction Network. The original Ray Prediction Network predicts obstacle-distance rays from camera input; in this Go2 adaptation, D435i depth is converted into forward rays and MID360 LiDAR supplies side/rear distance observations. This section follows the practical sequence: environment setup → Go1-to-Go2 port → initial Sim-to-Real test (revealing the gap) → Real-to-Sim calibration → observation/task adjustments → evaluation and troubleshooting.

0. Environment Setup

Follow the version combination in the official README to avoid compatibility problems:

conda create -n abs python=3.8 -y
conda activate abs
pip install torch==2.0.1 torchvision==0.15.2 torchaudio==2.0.2 \
    --extra-index-url https://download.pytorch.org/whl/cu116

# 2) Isaac Gym Preview 4 (download the tarball manually)
cd isaacgym/python && pip install -e .
# Sanity check:
cd examples && python 1080_balls_of_solitude.py

# 3) Install the ABS repository locally
cd ABS/training
pip install -e rsl_rl          # ABS-modified rsl_rl; install it from the ABS directory
pip install -e legged_gym

# 4) Pin older dependencies to avoid conflicts with Isaac Gym
pip install "numpy>1.20,<1.24"   # 1.21 was the most stable in testing
pip install tensorboard
pip install setuptools==59.5.0

Common pitfalls:

  • numpy ≥ 1.24 can crash Isaac Gym when it parses array types.
  • A newer setuptools release can break pip install -e.
  • A driver/CUDA mismatch with PyTorch or Isaac Gym can cause CUDA OOM or illegal memory access when num_envs is large. First validate with --num_envs=64, then scale up.

1. Porting the Training Task from Go1 to Go2

The original ABS repository only defines Go1 tasks, so the training pipeline must be ported to Go2. Affected files (paths relative to training/legged_gym/legged_gym/):

  • Add a URDF: resources/robots/go2/urdf/go2_description.urdf (from Unitree’s official Go2 description package, including meshes).
  • Add Go2 configurations: copy the three configurations from envs/go1/ into envs/go2/: go2_config.py / go2_pos_config.py / go2_rec_config.py, then update each item:
    • asset.file: go1.urdf → go2_description.urdf; asset.name = "go2".
    • init_state.pos: Go1 standing height 0.37 m → measured Go2 height 0.34 m (Go2 legs are slightly shorter).
    • init_state.default_joint_angles: retain the FL/FR/RL/RR_{hip,thigh,calf}_joint naming scheme (Go2 uses the same joint names), but use thigh = 0.9 and calf = -1.8 to match Go2 leg proportions (Go1 uses 0.8 / -1.5).
    • control.stiffness / damping: Go1 uses 30 / 0.65; Go2 motors are stiffer, so the initial values follow Unitree SDK defaults: 40 / 1.0 before further tuning.
    • asset.foot_name remains "foot"; the contact-penalty link names "thigh"/"calf" remain unchanged.
  • Add a LiDAR-enhanced configuration: create go2_pos_lidar_config.py; num_observations changes from 50+21=71 to 50+11+13=74 to include side/rear 2D LiDAR observations.
  • Register the tasks: edit envs/__init__.py, adding: 
    task_registry.register("go2_rough",            LeggedRobot,    Go2RoughCfg(),         Go2RoughCfgPPO())
task_registry.register("go2_pos_rough",        LeggedRobotPos, Go2PosRoughCfg(),      Go2PosRoughCfgPPO())
task_registry.register("go2_pos_lidar_rough",  LeggedRobotPos, Go2PosLidarRoughCfg(), Go2PosLidarRoughCfgPPO())
task_registry.register("go2_rec_rough",        LeggedRobotRec, Go2RecRoughCfg(),      Go2RecRoughCfgPPO())
# And the corresponding PPO-Lagrangian variants

After this step, python scripts/train.py --task=go2_pos_rough --num_envs=64 should run with an increasing reward curve, indicating that the port works.

2. Initial Sim-to-Real Test: Deploying the Simulation Policy Directly

This step makes no adjustments; its purpose is to expose the gap. Train the Agile Policy (go2_pos_rough, 4,000 iterations) with Go1’s default domain randomization, export it to .onnx, and deploy it on Go2. Typical observed issues:

  • Pitching during acceleration/deceleration and launch overshoot: command changes cause visible base pitch, suggesting that the forward-mounted sensor mass is missing from the URDF and the payload model needs correction.
  • Joint saturation and stuttering during sharp turns: the robot cannot reproduce rapid motions seen in simulation, pointing to the torque-speed envelope.
  • Periodic jumps in the goal vector: localization updates more slowly than the policy, motivating localization-latency randomization.
  • Nearby obstacles disappear: the D435i produces depth holes at close range, while simulated rays are always valid, motivating ray-noise and dropout randomization.

These observations form the input list for the next Real-to-Sim step.

3. Real-to-Sim (A): URDF Payload Correction

  • The original URDF uses bare-Go2 inertia (base 6.921 kg). This reproduction treats RealSense D435i (0.072 kg @ [0.31, 0, 0.10] m) and Livox MID360 (0.265 kg @ [0.15, 0, 0.13] m) as rigid point masses and incorporates them into base_link:
    • <inertial><mass>: 6.921 → 7.258 kg
    • <origin> (center of mass): origin → approximately 1–2 cm forward along +x (weighted by mass)
    • <inertia>: use the parallel-axis theorem to add the point-mass contributions to ixx / iyy / izz (the pitch inertia iyy increases the most)
  • Rationale: the sensors are mounted forward on an overhang, so their inertia contribution scales with mass × distance². Without this correction, simulation underestimates pitch inertia, and acceleration/deceleration actions learned by the policy can produce pitching and overshoot on the robot, matching the observations in step 2.

4. Real-to-Sim (B): Feeding Measured Latency and Torque into Domain Randomization

On Go2, use tools/measure_sim2real_gap.py and measure_joint_limits_readonly.py to record: end-to-end latency from policy output to joint motion, each joint’s peak torque-speed curve, and joint zero offsets while standing; then update go2_pos_config.py in the class domain_rand and class asset:

  • Joint response: armature = 0.01 (reflected gear-motor inertia; Go1 defaults to 0, making simulated joints too responsive).
  • Action latency: action_latency_range = [0, 1] steps (measured sense-to-actuate latency ≈ 9 ms at a 50 Hz control rate).
  • Localization latency/jitter (matching the real Livox-LIO system): loc_latency_range = [1, 3] steps, loc_update_decimation = 2 (LIO ≈ 25 Hz), yaw random walk loc_yaw_drift_std = 0.005 rad/step, with a maximum bias of 0.10 rad.
  • Torque-speed derating: torque_speed_derate = True; construct a linear envelope from URDF peak torque and maximum speed (10% floor) to prevent the policy from learning sharp motions that the robot cannot execute.
  • Forward-perception latency: front_lidar_latency_range = [1, 3] steps, decimation 2 (D435i-to-ray ≈ 23 ms, slower than the control loop).
  • External disturbances: max_push_vel_xy 0.0 → 0.5; re-enable random pushes to encourage policy robustness.

5. Changing Perception and Localization (Coupled to Simulation Observations)

Specific node changes are described in Deployment, but they directly determine how simulation observations are constructed, so the simulation configuration must change accordingly:

  • Forward camera: ZED mini → RealSense D435i. ZED mini provides VIO poses, whereas D435i provides depth and IMU data but no VIO pose. This leads to two changes:
    1. The simulation cannot retain all 21 original rays. Given the D435i usable field of view and onboard compute budget, change sensors.ray2d.theta_step from π/40 (4.5°, 21 rays) to π/20 (9°, 11 rays).
    2. Pose no longer comes from the forward camera; a localization node supplies it (see below).
  • Localization: camera VIO → odometry from Livox MID360 + LIO. This change is mainly on the robot. In simulation, the policy observations treat the goal vector and heading as delayed, noisy, and low-frequency signals during training:
    • add white noise to commands via noise_scales.commands = 0.03
    • reduce the update rate with loc_update_decimation = 2 (25 Hz)
    • accumulate yaw drift (see section 4)
    The resulting policy does not assume that localization is noise-free.
  • Add side/rear 2D LiDAR observations from MID360 slices: in simulation, append 13 side_rear_lidar2d dimensions in go2_pos_lidar_config.py, increasing the policy MLP input from 71 to 74.

6. Adjusting Task Scope

  • Goal-sampling range: commands.ranges.pos_1 0.3–3.0 m → 0.2–6.0 m, covering a larger laboratory space while retaining close-range training examples so the policy does not make wide detours near a goal.
  • Episode length: env.episode_length_s 9 s → 12 s (longer goal distances require more time).
  • Obstacle density: asset.object_num keep 8 depending on the site; use 4–6 in a more open laboratory.

7. Training Commands and Outputs

After all Real-to-Sim changes are in place, retrain in this order. Convert the resulting .pt models to .onnx for deployment with deployment/src/abs_src/onnx_model_converter.py:

# 1) Agile Policy (Go2, with LiDAR observations)
python scripts/train.py --task=go2_pos_lidar_rough --max_iterations=4000

# 2) Recovery Policy
python scripts/train.py --task=go2_rec_rough --max_iterations=1000

# 3) Run play once to export the policy directory, then train Reach-Avoid
python scripts/play.py    --task=go2_pos_lidar_rough
python scripts/testbed.py --task=go2_pos_lidar_rough --num_envs=1000 --headless --trainRA

# 4) Collect ray training data and train the Ray Prediction Network
python scripts/camrec.py            --task=go2_pos_lidar_rough --num_envs=3
python scripts/train_depth_resnet.py

8. Simulation Evaluation Protocol

  • Track reward, episode length, collision rate, and success rate in TensorBoard; baseline-versus-Real-to-Sim comparisons provide the clearest diagnostic view.
  • Use play_lidar_eval.py for randomized-scenario evaluation and record success rate, mean time to goal, maximum forward velocity, and collision rate under a fixed protocol. Comparisons with Table I in the original paper require matched conditions.

9. Simulation Diagnostics

  • Record each engineering issue as symptom → diagnosis → resolution. Representative diagnostic categories include: joint oscillation with armature=0 / freezing the Agile Policy before RA value converges / GPU OOM with too many environments / latency doubling when simulation timestep and control decimation disagree / init_dof sampling overflow because Go2 and Go1 share joint names but have different limits.

Deployment

Deployment uses the ABS ROS pipeline, but changes the robot from Go1 to Go2 and the forward camera from ZED mini to RealSense D435i, while adding Livox MID360 for side/rear 2D LiDAR observations and LIO localization. The nodes run on an onboard Orin NX (16 GB) and send joint commands through the Unitree Go2 low-level control interface.

1. Hardware Platform

  • Robot: Unitree Go2 EDU (replacing Go1)
  • Forward perception: Intel RealSense D435i (replacing ZED mini)
  • Side/rear perception and localization: Livox MID360 (added)
  • Onboard compute: NVIDIA Jetson Orin NX 16 GB
  • Status indication: PSEQT LED Lights (retained from the original setup)
  • Power: Pololu 12V 15A Step-Down Regulator D24V150F12

2. Perception Pipeline Adaptation

  • Forward depth to rays: add d435_preprocess_node / publisher_depthimg_linvel_d435.py, and extract nearest-obstacle distances along 11 evenly spaced rays from D435i depth images, publishing /odom_linvel as the policy’s estimated base linear velocity.
  • Side/rear 2D LiDAR: add livox_side_lidar_node / print_zed_front_lidar; slice the MID360 3D point cloud at base height to obtain 2D distances and feed 13 additional observation dimensions to the go2_pos_lidar policy.
  • Localization: MID360 + LIO provides /Odometry at approximately 25 Hz; downstream nodes interpolate poses and clip noise.
  • Model conversion: convert trained .pt models (agile / recovery / RA) to .onnx with onnx_model_converter.py for inference on Orin NX with ONNXRuntime.

3. ROS Nodes and Startup Order

# 1) ROS and Go2 low-level mode
roscore
# Controller: L2+A → L2+B → L1+L2+Start to enter low-level control

# 2) Sensor preprocessing and localization
python publisher_depthimg_linvel_d435.py            # D435i depth → rays + linear velocity
rosrun livox_ros_driver2 livox_ros_driver2_node     # MID360 point cloud
roslaunch fast_lio mapping.launch                   # LIO → /Odometry

# 3) LED safety indication (color determined by RA value)
python led_control_ros.py

# 4) Main controller (agile/recovery switching and Go2 joint commands)
python depth_obstacle_depth_goal_ros.py

In the full ABS controller design, the Agile Policy runs by default; when the RA value falls below the threshold, the Recovery Policy takes over to return the robot to the safe set, while the LED turns red to alert the operator. The real-world rollouts on this project page document the Agile Policy deployment path.

4. Controller Mapping

  • B: emergency stop
  • Default: run ABS according to goal commands
  • L2 / R2: turn left / right
  • Down / Up: move backward / stand
  • A: turn in place
  • X: return to the initial position

5. Real-World Evaluation Protocol

  • For quantitative evaluation, record success rate, collision count, and maximum forward velocity over repeated trials under a fixed setup.
  • The homepage rollout gallery provides qualitative deployment evidence; aggregate performance claims should remain tied to logged evaluation trials.

6. Deployment Diagnostics

  • Organize deployment issues as symptom → diagnosis → resolution. Representative cases include: D435i depth holes causing ray jumps (median filtering + reuse the previous valid value) / LIO yaw drift during fast turns (increase IMU weighting / limit angular velocity) / pitching due to torque saturation (retrain with torque_speed_derate) / differences between Go2 SDK and Go1 joint ordering.

7. Scope of Reported Results

This technical record documents the implemented simulation and real-world deployment workflow. Numerical success rates and speed comparisons should be reported only from matched, repeatable evaluation logs.
