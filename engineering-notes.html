复现说明 Overview

原工作。 Agile But Safe (ABS, RSS 2024) 让四足机器人在杂乱环境中 高速移动的同时避免碰撞：用一个敏捷策略 (agile policy) 追求速度， 一个恢复策略 (recovery policy) 在危险时接管，两者由一个基于 可达性 (reach-avoid) 值函数的安全门限协同切换，并配合一个 从感知预测碰撞风险的网络。

本复现的定位。 本项目不是简单跑通官方代码，而是把 ABS 迁移到本实验室的硬件平台 —— Unitree Go2 + RealSense D435i （前向深度→2D ray）+ Livox MID360（侧/后向 2D lidar 与 LIO 定位） —— 并把工作重心放在 sim2real gap 的量化与对齐：先在实机上测量延迟、 负载、电机特性，再把这些测量值回灌进仿真 (real2sim) 做域随机化， 让训练出的策略在真机上可用。训练在 Isaac Gym 完成， 部署为一套 ROS 节点。

系统总览

仿真部分 Simulation

仿真侧基于 ABS 官方代码（training/legged_gym + training/rsl_rl， Isaac Gym Preview 4）。按原文要训四个组件： (1) 敏捷策略 agile policy（PPO）、 (2) 恢复策略 recovery policy、 (3) Reach-Avoid 值函数、 (4) 射线预测网络 ray-prediction。 本节按真实推进顺序写：搭环境 → Go1→Go2 移植 → 首轮 sim2real（暴露 gap） → real2sim 反推回仿真 → 观测/任务调整 → 评测/踩坑。

0. 环境搭建

严格按官方 README 的版本组合来，少踩坑：

# 1) Python 3.8 + PyTorch（CUDA 11.6）
conda create -n abs python=3.8 -y
conda activate abs
pip install torch==2.0.1 torchvision==0.15.2 torchaudio==2.0.2 \
    --extra-index-url https://download.pytorch.org/whl/cu116

# 2) Isaac Gym Preview 4（需手动下载 tar 包）
cd isaacgym/python && pip install -e .
# 自检：
cd examples && python 1080_balls_of_solitude.py

# 3) ABS 仓库本地化
cd ABS/training
pip install -e rsl_rl          # ABS 改过的 rsl_rl，必须从 ABS 目录装
pip install -e legged_gym

# 4) 老版本依赖钉死，否则会和 Isaac Gym 冲突
pip install "numpy>1.20,<1.24"   # 实测 1.21 最稳
pip install tensorboard
pip install setuptools==59.5.0

常见坑：

  • numpy ≥ 1.24 会让 Isaac Gym 在解析数组类型时崩。
  • setuptools 太新会让 pip install -e 失败。
  • 驱动 / CUDA 版本与 PyTorch / Isaac Gym 任一不匹配， num_envs 一大就 CUDA OOM 或 illegal memory access。 先用 --num_envs=64 调通再放大。

1. 把训练目标从 Go1 切到 Go2

ABS 原仓库只给 Go1 的任务，所以要把整套训练流程平移到 Go2。 涉及的文件清单（路径相对 training/legged_gym/legged_gym/）：

  • 新增 URDF：resources/robots/go2/urdf/go2_description.urdf （取自 Unitree 官方 go2 描述包，含 mesh）。
  • 新增 Go2 配置：把 envs/go1/ 下的三份配置整体复制成 envs/go2/：go2_config.py / go2_pos_config.py / go2_rec_config.py，逐项改：
    • asset.file：go1.urdf → go2_description.urdf；asset.name = "go2"。
    • init_state.pos：Go1 站高 0.37 m → Go2 实测 0.34 m（Go2 腿稍短）。
    • init_state.default_joint_angles：保留 FL/FR/RL/RR_{hip,thigh,calf}_joint 命名（Go2 关节名一致）， 但 thigh = 0.9、calf = -1.8 以匹配 Go2 的腿长比例（Go1 是 0.8 / -1.5）。
    • control.stiffness / damping：Go1 用 30 / 0.65， Go2 电机更"硬"，初版按 Unitree SDK 默认改为 40 / 1.0 再回归调。
    • asset.foot_name 保持 "foot"， 接触惩罚 link 名 "thigh"/"calf" 不变。
  • 新增 lidar 增强配置：再复制一份 go2_pos_lidar_config.py，num_observations 从 50+21=71 改成 50+11+13=74，给侧/后 2D lidar 留位置。
  • 注册任务：编辑 envs/__init__.py，加： 
    task_registry.register("go2_rough",            LeggedRobot,    Go2RoughCfg(),         Go2RoughCfgPPO())
task_registry.register("go2_pos_rough",        LeggedRobotPos, Go2PosRoughCfg(),      Go2PosRoughCfgPPO())
task_registry.register("go2_pos_lidar_rough",  LeggedRobotPos, Go2PosLidarRoughCfg(), Go2PosLidarRoughCfgPPO())
task_registry.register("go2_rec_rough",        LeggedRobotRec, Go2RecRoughCfg(),      Go2RecRoughCfgPPO())
# 以及对应的 PPO-Lagrangian 变体

这一步做完，python scripts/train.py --task=go2_pos_rough --num_envs=64 能跑起来 reward 曲线在涨，就算移植通了。

2. 首轮 sim2real：把仿真策略直接丢到真机上

这一步不调任何东西，目的就是暴露 gap。用 Go1 默认的域随机化训出 agile policy（go2_pos_rough，4000 iters），导出 .onnx 部署到 Go2 上跑。观察到的典型问题：

  • 加减速点头 / 起步过冲：策略命令变化时基座俯仰幅度明显， 怀疑悬臂传感器质量没进 URDF → 指向 URDF 负载修正。
  • 急转时关节饱和、动作"卡顿"：仿真里能做的急摆真机做不出来 → 指向力矩-转速包络。
  • 目标向量周期性跳变：定位刷新慢于策略 → 指向定位延迟域随机化。
  • 近距离障碍突然消失：D435i 在贴近时出深度空洞， 而仿真 ray 总是有效 → 指向 ray 噪声/丢值的域随机化。

这些观察就是下一步 real2sim 的输入清单。

3. real2sim（A）：URDF 负载修正

  • 原 URDF 用的是裸 Go2 惯量（base 6.921 kg）。本复现把 RealSense D435i (0.072 kg @ [0.31, 0, 0.10] m) 与 Livox MID360 (0.265 kg @ [0.15, 0, 0.13] m) 当作刚性点质量， 用平行轴定理合并进 base_link：
    • <inertial><mass>：6.921 → 7.258 kg
    • <origin>（质心）：原点 → 沿 +x 前移约 1–2 cm （按质量加权）
    • <inertia>：用平行轴定理把两个点质量贡献到 ixx / iyy / izz（俯仰 iyy 增加最明显）
  • 动机：传感器都是悬臂前装，悬臂力矩 = 质量 × 距离²， 不修正会让仿真低估俯仰惯量。结果是策略学到的加减速动作 真机上点头/过冲，正好对应第 2 步观察到的现象。

4. real2sim（B）：实测延迟/力矩灌回域随机化

在 Go2 上用 tools/measure_sim2real_gap.py 与 measure_joint_limits_readonly.py 记录： policy 输出到关节真正动的端到端延迟、各关节峰值力矩-转速曲线、 站立时关节回零偏置；然后改 go2_pos_config.py 的 class domain_rand 与 class asset：

  • 关节响应：armature = 0.01 （齿轮电机反射惯量，Go1 默认 0，仿真关节会过分"轻快"）。
  • 动作延迟：action_latency_range = [0, 1] 步 （实测 sense → actuate ≈ 9 ms，控制环 50 Hz）。
  • 定位延迟/抖动（对应实机的 Livox-LIO）： loc_latency_range = [1, 3] 步、 loc_update_decimation = 2（LIO ≈ 25 Hz）、 yaw 随机游走 loc_yaw_drift_std = 0.005 rad/step， 偏置上限 0.10 rad。
  • 力矩-转速衰减：torque_speed_derate = True， 用 URDF 峰值力矩 / 最大转速构造线性包络（floor 10%）， 防止策略学到真机做不出的急摆。
  • 前向感知延迟：front_lidar_latency_range = [1, 3] 步、 decimation 2（D435i → ray ≈ 23 ms，慢于控制环）。
  • 外扰：max_push_vel_xy 0.0 → 0.5， 重新开启随机推力，逼策略学鲁棒。

5. 感知与定位方式切换（与仿真观测耦合）

这一步的具体节点改动在 部署部分，但它直接决定 仿真侧观测如何构造，所以仿真 config 必须同步调整：

  • 前向相机：ZED mini → RealSense D435i。ZED mini 自带 VIO 输出位姿，D435i 没有，只给深度图 + IMU。这导致两个连锁改动：
    1. 仿真 ray 不能再按"原 21 条"全用上：D435i 实际可用 FOV 与板载算力匹配下，把 sensors.ray2d.theta_step 从 π/40 (4.5°, 21 条) 改成 π/20 (9°, 11 条)。
    2. 位姿不再来自前向相机，改用定位节点给（见下条）。
  • 定位：相机 VIO → Livox MID360 + LIO 推出的 odom。 这一步主要在实机上做，仿真里的体现是：策略观测中的 "到目标向量 / 朝向"被显式当作带延迟、带噪声、低频更新的量来训：
    • 对 commands 加白噪声 noise_scales.commands = 0.03
    • 更新频率打折 loc_update_decimation = 2（25 Hz）
    • 累积 yaw drift（见第 4 节）
    这样训出来的策略默认就不信任定位是干净的。
  • 新增侧 / 后向 2D lidar 观测（来自 MID360 切片）： 仿真里在 go2_pos_lidar_config.py 的观测里追加 13 维 side_rear_lidar2d，policy MLP 输入层从 71 拉到 74。

6. 任务范围调整

  • 目标采样范围：commands.ranges.pos_1 0.3–3.0 m → 0.2–6.0 m，覆盖实验室更大场地， 同时保留近距离训练样本，避免策略在近端绕大圈。
  • episode 长度：env.episode_length_s 9 s → 12 s（目标距离变远要相应给时间）。
  • 障碍密度：asset.object_num 视场地保持 8；若实验室空旷可调到 4–6。

7. 训练命令与产物

所有 real2sim 改动到位后，按下列顺序重训。产物 .pt 之后用 deployment/src/abs_src/onnx_model_converter.py 转为 .onnx 给部署节点调用：

# 1) 敏捷策略（Go2，带 lidar 观测）
python scripts/train.py --task=go2_pos_lidar_rough --max_iterations=4000

# 2) 恢复策略
python scripts/train.py --task=go2_rec_rough --max_iterations=1000

# 3) 先 play 一次导出 policy 文件夹，再训 Reach-Avoid
python scripts/play.py    --task=go2_pos_lidar_rough
python scripts/testbed.py --task=go2_pos_lidar_rough --num_envs=1000 --headless --trainRA

# 4) 采射线训练集 + 训 ray-prediction
python scripts/camrec.py            --task=go2_pos_lidar_rough --num_envs=3
python scripts/train_depth_resnet.py

部署部分 Deployment

部署侧基于 ABS 的 ROS pipeline，但本体由 Go1 → Go2，前视相机由 ZED mini → RealSense D435i，并额外引入 Livox MID360 做侧/后向 2D lidar 与 LIO 定位。整套节点跑在板载 Orin NX (16GB)， 通过 Unitree Go2 低层控制接口下发关节命令。

1. 硬件平台

  • Robot: Unitree Go2 EDU（替换原 Go1）
  • 前向感知: Intel RealSense D435i（替换原 ZED mini）
  • 侧 / 后向感知 + 定位: Livox MID360（新增）
  • 板载算力: NVIDIA Jetson Orin NX 16GB
  • 状态指示: PSEQT LED Lights（沿用原方案）
  • 电源: Pololu 12V 15A Step-Down Regulator D24V150F12

2. 感知管线适配

  • 前向深度 → ray：新增 d435_preprocess_node / publisher_depthimg_linvel_d435.py， 从 D435i 深度图沿 11 条等角射线取最近障碍物距离， 并发布 /odom_linvel 给策略当 base lin-vel 估计。
  • 侧 / 后向 2D lidar：新增 livox_side_lidar_node / print_zed_front_lidar，从 MID360 的 3D 点云按 base 高度切片得到 2D 距离，喂给 go2_pos_lidar 策略的 附加 13 维观测。
  • 定位：MID360 + LIO 提供 /Odometry，频率 ≈ 25 Hz； 下游节点对位姿再做插值与噪声裁剪。
  • 模型转换：训练得到的 .pt（agile / recovery / RA） 用 onnx_model_converter.py 转为 .onnx， 在 Orin NX 上以 ONNXRuntime 推理。

3. ROS 节点与启动顺序

# 1) ROS 与 Go2 低层模式
roscore
# 手柄: L2+A → L2+B → L1+L2+Start  进入低层控制

# 2) 传感器预处理 + 定位
python publisher_depthimg_linvel_d435.py            # D435i 深度 → ray + linvel
rosrun livox_ros_driver2 livox_ros_driver2_node     # MID360 点云
roslaunch fast_lio mapping.launch                   # LIO → /Odometry

# 3) LED 安全指示（颜色由 RA value 决定）
python led_control_ros.py

# 4) 主控（agile + recovery 切换 + Go2 下发关节）
python depth_obstacle_depth_goal_ros.py

主控里同时挂着两份策略：agile 平时跑；当 RA 值跌破阈值，切 recovery 接管把机器人拽回安全集；LED 同步切红色提示操作者。

4. 手柄控制映射

  • B：紧急停止
  • Default：按目标命令运行 ABS
  • L2 / R2：左转 / 右转
  • Down / Up：后退 / 站立
  • A：原地转身
  • X：回到初始位置
